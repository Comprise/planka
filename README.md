# planka

Плагин Claude Code уровня пользователя: на каждую реплику подмешивает `philosophy.md` в
контекст, а в точках выбора — вопрос автору, выход из плана, сообщение со списком вариантов —
судья-модель отклоняет рекомендацию лёгкого пути вместо правильного. Судья проверяет и заявку
«готово», сверку документации после правки кода и запись в постоянную память; детерминированные
проверки отклоняют новую зависимость без согласия автора — командой установки или правкой манифеста — и
пересечение файлов в волне плана, а повторная неудача команды подмешивает агенту модуль отладки.

## Установка

Плагин ставится только из маркетплейса (манифест `.claude-plugin/marketplace.json`). Id плагина —
`planka@planka`.

Удалённый маркетплейс, репозиторий `github.com/Comprise/planka`:

```bash
claude plugin marketplace add Comprise/planka
claude plugin install planka@planka
```

Для разработки — маркетплейс из рабочей копии (путь клона, например `~/Projects/planka`):

```bash
claude plugin marketplace add ~/Projects/planka
claude plugin install planka@planka
```

Установленный плагин — копия в `~/.claude/plugins/cache/planka/planka/<version>/`: правки рабочей
копии в неё сами не попадают. Обновление — `claude plugin marketplace update planka`, затем
`claude plugin update planka@planka` и перезапуск сессии; подхватит ли обновление правки при той же
`version` в `plugin/.claude-plugin/plugin.json`, не проверено.

Языки по умолчанию — `ru`; другие задаются так:

```bash
claude plugin configure planka@planka --values-stdin <<< '{"comment_lang":"en+ru","doc_lang":"ru"}'
```

Переход со старой установки ссылкой: если `claude plugin list` показывает `planka@skills-dir`,
перед добавлением маркетплейса выполнить `rm ~/.claude/skills/planka`: иначе один плагин установлен дважды,
под двумя id.

Требования: POSIX — Linux, macOS, WSL (без `fcntl` каждый хук отвечает только предупреждением и ничего не
проверяет), `python3` 3.11+ (разбор TOML — `tomllib`), `claude` в `PATH`, вход в Claude Code выполнен (OAuth или ключ).

## Настройки

Задаются через `claude plugin configure <id>`; текущие значения — `claude plugin configure <id> --json`.
Список и умолчания — `userConfig` в `plugin/.claude-plugin/plugin.json`.

| Настройка | Значения | Действие |
| --- | --- | --- |
| `judge_model` | `session`, `sonnet`, `opus`, `haiku`, `fable`; по умолчанию `session` | модель вложенного судьи; `session` — модель текущей сессии |
| `comment_lang` | `en`, `ru`, `en+ru`; по умолчанию `ru` | язык комментариев в коде; `en+ru` — английский, затем русский перевод |
| `doc_lang` | `en`, `ru`; по умолчанию `ru` | язык `CLAUDE.md`, `context/`, `deferred/` |

Выключение плагина — `claude plugin disable <id>`. Переменных окружения для пользователя нет:
`PLANKA_JUDGE` — служебная метка вложенного вызова судьи (см. «Как это работает»).

Предупреждения и внутренние ошибки хуков доходят до пользователя полем `systemMessage` JSON-ответа
хука; stderr хуки не пишут.

## Как это работает

Плагин — каталог `plugin/` репозитория; пути ниже — от него.

Правила — это ядро `philosophy.md` и модули `rules/*.md` (по файлу на область, каждый начинается
с условия «Читайте, мой дорогой друг, …»), среди них `docs.md` (документация проекта) и `comments.md`
(комментарии в коде).

Всё, что плагин пишет моделям, — ядро, модули, промпты судьи, причины отказа и блока, контекст хуков — на «вы», с
«пожалуйста» в просьбах. Причина отказа и блока и контекст хука начинаются обращением «Мой дорогой друг»
(`prompts.ADDRESS`), которое ставит хук; промпты судьи начинаются им же. Предупреждения пользователю
(`systemMessage`) обращения не имеют.

Хуки (`hooks/hooks.json`):

| Событие | Скрипт | Таймаут | Что делает |
| --- | --- | --- | --- |
| `SessionStart` | `planka/model_watch.py` | 10 с | запоминает модель сессии для судьи |
| `UserPromptSubmit` | `planka/remind.py 1` | 10 с | часть 1 ядра в контекст, снимок дерева |
| `UserPromptSubmit` | `planka/remind.py 2` | 5 с | часть 2 ядра в контекст |
| `PreToolUse` на `AskUserQuestion`, `ExitPlanMode`, `Bash`, `Write`, `Edit`, `MultiEdit` | `planka/judge_tool.py` | 90 с | судья вопроса и плана, детектор зависимостей, правка манифеста, снимок манифестов перед командой |
| `PreToolUse` на `Write`, `Edit`, `MultiEdit`, `NotebookEdit` и MCP-инструменты с `memor` или `remember` в имени (без учёта регистра) | `planka/guard_memory.py` | 90 с | судья записи в постоянную память |
| `Stop` | `planka/judge_stop.py` | 120 с | фильтры «варианты», «готово», «документация» и судья |
| `PostToolUse` и `PostToolUseFailure` на `Bash` | `planka/debug_watch.py` | 10 с | модуль `debugging.md` на повторной неудаче команды |
| `PostToolUse` и `PostToolUseFailure` на `Bash` | `planka/judge_tool.py` | 30 с | новые зависимости в манифестах после команды |
| `PostModelSwitch` | `planka/model_watch.py` | 10 с | запоминает новую модель сессии для судьи |

- `SessionStart` (поле `model`) и `PostModelSwitch` (поле `to_model`) → `planka/model_watch.py`: модель сессии в
  `state/<session>.model.json` для судьи (ниже, «Судья, лимит и журнал»); агенту хук ничего не выводит.
- `UserPromptSubmit` → `planka/remind.py 1` и `planka/remind.py 2`: ядро `philosophy.md` частями
  (`remind.PARTS`), каждая — отдельным `additionalContext` своего хука, вместе со строкой обращения не
  длиннее 10 000 символов
  (`remind.CONTEXT_LIMIT`: строку длиннее Claude Code сохраняет в файл и отдаёт агенту путь и первые 2 000
  символов). Ядро делится по разделам `## ` так, чтобы наибольшая часть была наименьшей; первая часть начинается
  заголовком ядра, следующие — заголовком «продолжение, часть k из N»: хуки одного события идут параллельно, и
  порядок частей не гарантирован. Часть длиннее предела выдаётся с предупреждением. Без номера в аргументе хук
  выдаёт часть 1. Строка «Проект без документации» и снимок дерева — только у части 1. В конце
  ядра — индекс «Модули»; метка `{RULES}` в ядре при чтении хуком заменяется абсолютным путём к
  каталогу `rules/` плагина, чтобы агент знал, где открыть модуль; модули ссылаются друг на друга
  так же — `{RULES}/<имя>.md`. Метки `{COMMENT_LANG}` и `{DOC_LANG}` хук подставляет значениями настроек в строку
  «Язык комментариев: …; язык документации: …» индекса и в модули, которые уходят судье; агент,
  открывший модуль с диска, видит метку и отсылку к этой строке индекса.
  Если в корне проекта нет `CLAUDE.md`, к контексту добавляется строка «Проект без документации:
  пожалуйста, предложите автору инициализацию по <каталог rules плагина>/docs.md.» Корень проекта — вершина git
  для `CLAUDE_PROJECT_DIR` (каталог запуска сессии; после `cd` агента он не меняется; без переменной —
  для `cwd`); вне git — сам этот каталог. Каталог запуска под домашним каталогом-репозиторием (dotfiles) или
  репозиторием выше дома, который под каталогом запуска не отслеживает ни одного файла, — сам корень: снимок идёт
  обходом каталога, `CLAUDE.md` ищется в нём, git о проекте не видит репозиторий выше. Новый или исключённый
  `.gitignore` подкаталог любого другого репозитория (монорепозиторий) — корень вершина.
  Хук части 1 снимает снимок дерева проекта для фильтра «документация» и пишет его в
  `state/<session>.snap.json`:
  - в git-репозитории — коммиты HEAD корня, инициализированных подмодулей и вложенных репозиториев,
    которые не подмодули, и размер и mtime путей, изменённых против HEAD или неотслеживаемых
    (`git status`: файлы из `.gitignore`, `.git/info/exclude` и глобального excludes в снимок не
    входят). Размер снимка от размера дерева не зависит; изменённых и неотслеживаемых путей больше
    `snapshot.MAX_FILES` (50 000) — снимок не делается, с предупреждением; неудача запоминается для корня
    проекта (`state/<session>.snapfail.json`), и до конца сессии снимок этого корня не повторяется;
  - вне git — размер и mtime каждого обычного файла обходом каталогов, сжатой записью по каталогам (zlib в
    base64); символические ссылки не обходятся; пропускаются каталоги из
    `snapshot.IGNORED_DIRS` (`.git`, `node_modules`, `__pycache__`, `.venv`, `venv`, `target`, `build`,
    `dist`, `.dart_tool`, `.data`, `.idea`, `.vscode`) и записи `.gitignore` каждого каталога без
    подстановочных знаков и вида `*.ext` — на поддереве этого каталога.

  Снимок — вызовы git, чтение размеров файлов и упаковка записи вне git — ограничен сроком 7 с от старта хука
  (`remind.SNAPSHOT_BUDGET`, при таймауте части 1 10 с), вне git числа файлов он не ограничивает: не уложился —
  снимок пропускается с предупреждением, напоминание выдаётся; неудача запоминается для корня, и до конца
  сессии снимок этого корня не повторяется. Сбой определения корня тоже не снимает напоминание: выдаётся
  предупреждение.
- `PreToolUse` на `AskUserQuestion`, `ExitPlanMode`, `Bash`, `Write`, `Edit`, `MultiEdit` (matcher
  `^(AskUserQuestion|ExitPlanMode|Bash|Write|Edit|MultiEdit)$`) → `planka/judge_tool.py`: вопрос — по
  разделу «Решения»; план — сначала детерминированная проверка владения файлами в волне, потом
  судья по «Решениям», «Планам» и модулям `planning.md`, `subagents.md`, `refactoring.md`,
  `design-patterns.md`, `heuristics.md`: кроме вопросов о вариантах — волны и схождение, контракт до задач,
  самодостаточность задач, общие файлы у координатора, последняя волна — независимое ревью диффа,
  классы входов и окружений для плана, который трогает разбор входа, хук, сервис или CLI,
  дешёвая ошибка и корпус настоящих входов для плана, который меняет эвристику или разборщик; у каждой
  задачи — что сделать, файлы во владении, что трогать нельзя, как проверить свой пакет, что сообщить
  координатору и что делать при проблеме. Текст плана берётся из файла, путь которого записан в
  транскрипте; нет пути, нет файла или он не читается — пропуск с предупреждением. Судья вопроса и плана видит
  прежние реплики автора (вместе — до 8000 символов, старые отбрасываются первыми), реплику текущего хода и
  ответы на `AskUserQuestion` после неё (каждое поле — до 8000 символов, `prompts.MAX_AUTHOR_FIELD`): явная
  просьба автора — и из прежней реплики, если позже её не отменили, — побеждает рубрику, сделанное по ней — не
  нарушение.
  Команда `Bash` — детектор зависимостей, без модели, и снимок манифестов проекта перед ней; `Write`,
  `Edit`, `MultiEdit` манифеста — проверка новых зависимостей правки (ниже, «Манифесты»).
- `PreToolUse` на запись в постоянную память → `planka/guard_memory.py` (ниже, «Запись в память»).
- `Stop` → `planka/judge_stop.py`: два текстовых фильтра по последнему сообщению агента и фильтр
  «документация» по изменениям дерева с момента снимка. Совпавшие фильтры — один вызов судьи и
  общий лимит отказов; судья видит сообщения агента за реплику по порядку и между ними вызовы инструментов
  (команда `Bash` или путь файла) с началом и концом их вывода, последним —
  `last_assistant_message` входа хука, всего не больше 30 000 символов (`prompts.MAX_TURN_CHARS`):
  сначала снимается вывод ранних вызовов («⟦вывод опущен⟧»), затем ранние шаги сверх предела опущены строкой
  «… ранние шаги реплики опущены: N», от
  последнего шага длиннее предела остаётся конец: у сообщения — конец текста, у вызова — строка вызова и конец
  вывода. Метки шагов («⟦вызов …⟧», «⟦вывод⟧») и разделитель «---» ставит только хук: знаки ⟦ и ⟧ и строка из
  трёх и более «-» в тексте агента, команде и выводе идут судье за обратной косой, и поддельный шаг судья видит
  как данные. Реплику автора и его ответы судья `Stop` видит
  так же, как судья вопроса. На фильтре «варианты» судья проверяет и опоры рекомендации («Решения» 4): у
  утверждения о коде, данных или поведении, на котором она держится, назван источник — вызов в реплике,
  прочитанный файл, правило или `CLAUDE.md`, слова автора, проверка в прошлой реплике — или оно названо
  допущением; утверждение, которому противоречит вывод вызова в реплике, — нарушение. Судьи вопроса и плана
  вызовов инструментов не видят: этот пункт из их рубрики вырезается.
- `PostToolUse` и `PostToolUseFailure` на `Bash` → `planka/debug_watch.py` (ниже, «Повторная
  неудача команды») и `planka/judge_tool.py` — сравнение манифестов со снимком перед командой (ниже,
  «Манифесты»).

Рубрики судьи:

| Хук | Срабатывает | Рубрика |
| --- | --- | --- |
| `AskUserQuestion` | всегда | «Решения» |
| `ExitPlanMode` | всегда | «Решения» + «Планы» + `planning.md` + `subagents.md` + `refactoring.md` + `design-patterns.md` + `heuristics.md` |
| запись в память | цель — файл или MCP-инструмент постоянной памяти | «Границы» + `memory.md` |
| `Stop`, фильтр «варианты» | в последнем сообщении 2+ пункта списка и целое слово «рекоменд…», «вариант…», «подход», «способ», «выбор» в формах существительного, «предлага…», «совету…», `recommend…`, `option(s)` (кроме `Option<…>`, `Option::`) или `approach(es)` | «Решения» |
| `Stop`, фильтр «готово» | в последнем сообщении слово из списка ниже | `verification.md` |
| `Stop`, фильтр «документация» | со снимка текущей реплики изменился хотя бы один файл кода | `docs.md` + `comments.md` |

Слова фильтра «готово» (регистр не важен, целое слово): «готово/готова/готовы», «готов» перед
знаком препинания или концом строки («Фикс готов.»), «сделан», «исправлен», «починен»,
«выполнен», «завершён/завершен» с окончаниями -о/-а/-ы, «проходит», «проходят», «прошёл»,
«прошли», «зелёный» и его формы, `done`, `fixed`, `passing`, `passes`, `passed`, `succeeded`,
`succeeds`, `complete`, `completed`; прошедшее время «исправил», «поправил», «починил», «сделал», «доделал»,
«реализовал», «добавил», «закончил», «завершил» (и формы на -а/-и); «работает/работают» после «всё», «все»,
«теперь», «снова», «уже». Если совпало несколько фильтров, судья вызывается один раз:
рубрика и вопросы объединены. Судья «готово» проверяет, что названа команда-доказательство и
процитирован её увиденный вывод, что команда взята из CI-конфига, манифеста или task runner, что
названо непроверенное, что для фикса бага прогнан исходный сценарий, что числа взяты из вывода и
что добавленный к фиксу или фиче тест показан красным на коде до правки или на мутации и зелёным
после.
Сообщение без заявки о выполненной работе («готовы обсудить») проходит; в проекте без CI-конфига,
манифеста и task runner требование взять команду оттуда соблюдено. Судья «варианты» пропускает
сообщение без выбора между вариантами (отчёт, перечень сделанного). Если агент не заявляет работу
законченной, а ждёт ответа автора (задал вопрос или просит согласия), судья «документация» не требует
сверки `CLAUDE.md`, `context/` и записи остатка; комментарии проверяются и тогда.

Фильтр «документация»: каждый изменённый файл относится к одному из трёх классов. Код — файл с
расширением из `CODE_EXTS` (`common.py`: go, c, cpp, java, kt, swift, js, mjs, ts, mts, dart, rs,
cs, py, pyi, sh, rb, toml, yaml, ini, cmake, sql, lua, html, xml, css, scss, sass, less и другие)
или с именем из `CODE_NAMES` (`Makefile`, `makefile`, `GNUmakefile`, `CMakeLists.txt`, `Dockerfile`,
`Justfile`, `Rakefile`, `Gemfile` и манифесты `package.json`, `tsconfig.json`, `jsconfig.json`,
`composer.json`, `deno.json`, `go.mod`), в любом каталоге. Документация — остальные `*.md`,
`README*`, `LICENSE*` и всё под `context/` и `docs/` от корня. Прочее — всё остальное, в том числе
прочие `*.json` и `go.sum`. Фильтр запускает изменённый, добавленный или удалённый файл кода;
изменение файлов «прочее» и документации его не запускает.

Изменённые за реплику файлы: в git — отличные от коммита HEAD на старте реплики (коммит в ходе
реплики их не прячет; так же по каждому подмодулю и вложенному репозиторию) и изменённые или
неотслеживаемые сейчас; файл, изменённый ещё до реплики и не тронутый за неё (тот же размер и mtime),
не считается. Новый за реплику вложенный репозиторий — все его файлы. Вне git — разница двух обходов.
Сверка ограничена сроком `judge_stop.SNAPSHOT_BUDGET` (20 с). Если изменения определить нельзя — за
реплику корень стал или перестал быть git-репозиторием, пропал репозиторий снимка, коммит HEAD
снимка недоступен, срок вышел, — фильтр «документация» не срабатывает, с предупреждением. Снимка нет
или он прошлого формата (`snapshot.FORMAT`; плагин обновлён посреди реплики) — фильтр не срабатывает молча.

На прерванную автором реплику `Stop` не приходит: её снимок остаётся базой следующей реплики того же корня, и
правки прерванной реплики проверяются на `Stop` следующей. `Stop` отмечает снимок проверенным, если не
заблокировал, — в том числе при пропуске из-за ошибки судьи, лимита отказов или неопределимых изменений и при
внутренней ошибке хука после вердикта «без нарушений» или пропуска; после
блока снимок остаётся базой, пока следующий `Stop` не пройдёт без блока.

Судья видит сообщения агента за реплику, список изменённых файлов с пометками «код»,
«документация» и «прочее» (удалённый файл — с пометкой «удалён»; список не длиннее `MAX_LISTED` = 100,
остаток — строкой «и ещё N»), строки комментариев из изменённых файлов кода и, если в корне нет
`CLAUDE.md`, строку об этом. Строки комментариев: файл кода разбирается целиком, судье уходят
комментарии строк, добавленных против коммита HEAD на старте реплики (номера строк — по заголовкам
`@@` диффа); для файла подмодуля или вложенного репозитория — против его HEAD на старте реплики;
файл, переименованный через `git mv` или `git add` (git находит пару по сходству), — против старого
пути; атрибуты `-diff` и `binary` в `.gitattributes` отбор строк не сбивают. Для неотслеживаемого
файла, вне git и в репозитории без коммитов — комментарии всего файла. Синтаксисы — по расширению или
имени файла:

- `//` и `/* */` — go, c, cpp, java, kt, scala, swift, js, ts, dart, rs, cs, php, groovy, proto, sol,
  tf и др.; в scss, sass, less `//` сразу после `:` (`url(http://…)`) — не комментарий; JSONC-манифесты
  `tsconfig.json`, `jsconfig.json`, `deno.json`; `//` и `(* *)` — fs, fsx, fsi (`(*)` — оператор);
- только `//` — zig (строки `\\` — данные), `go.mod`; `/* */` без `//` — css, sql, nix;
- `#` — py, sh, rb, pl, pm, r, toml, yaml, ini, cfg, mk, cmake, ps1, tf, nix, jl, ex, php, nim и файлы по
  имени (`Makefile`, `CMakeLists.txt`, `Dockerfile` и др.); в sh, bash, zsh, yaml, `Dockerfile` и строках
  рецептов mk и `Makefile` (с табуляции; и сразу за префиксами `@`, `-`, `+`: `@# note` — комментарий) — только с
  начала слова (`ARG A=${B#x}`, `echo '#define X'` — значения), в остальных, кроме php и nim, `#` сразу после `$`,
  `{` или `\` — код (`$#a`, `${#x}`, `a\#b`);
  `#!` в первой строке у py, sh, rb, jl, ex, php, ps1, nim, nix и др. — не комментарий, в том числе после BOM; тело
  heredoc в shell, tf, rb, pl, php (`<<<ID`, `<<<"ID"`, `<<<'ID'`), `Rakefile`, `Gemfile` — данные (у rb
  и pl `<<ID`, `<<-ID`, `<<~ID`, в pl и с пробелом перед идентификатором в кавычках — `<< "ID"`, в rb это добавление;
  `<<` вплотную после слова или скобки — сдвиг: `1<<BITS`, `print $fh<<EOF`, кроме: в Ruby — ключевых слов, за которыми
  начинается выражение (`return<<EOS`), в Perl — встроенных функций, ждущих аргумент (`print<<EOT`, `lc<<EOS`),
  дескриптора из заглавных букв и `_` за `print`, `printf`, `say` (`print CSS<<EOF`) и блока-дескриптора
  (`print{$fh}<<EOF`) — там heredoc; после пробела за скобкой, кавычкой или переменной `$a`, `@a` — сдвиг (в Perl
  исключение: дескриптор после `print`, `printf`, `say` — `$fh`, `{$fh}`, `{$DB::OUT}`, `{$self->{fh}}`, `{*STDOUT}`
  любой длины, `STDOUT`, `STDERR` — heredoc); за словом Ruby — как у Ruby: за методом и константой heredoc
  (`puts <<eof`), за локальной переменной, числом, `self`, `nil`, `true`, `false` — сдвиг и добавление; за
  встроенной функцией Perl, ждущей аргумент, — heredoc, без аргументов (`time`, `__LINE__`) — сдвиг; за прочим словом
  Perl — heredoc, только если идентификатор с `-`, `~`, в кавычках или с заглавной буквы (ведущие `_` не в счёт:
  `<<_EOUSAGE_`); heredoc rb, pl и tf без строки-терминатора до конца файла — не heredoc,
  его строки разбираются как код); для py и pyi ещё docstring — строка, которая начинается с тройных
  кавычек; Ruby `=begin`…`=end` и Perl POD (`=слово`…`=cut`) с первой колонки — комментарий целиком (`=begin`
  внутри многострочной строки Ruby — текст строки; POD — только где Perl ждёт новый оператор: в начале файла, после
  `;`, `{`, `}` или метки, а посреди оператора `=shift` — присваивание); в Perl `-s` перед знаком не слова
  (`-s($f)`) — файловый тест, не замена `s`;
- `;` — ini, cfg (с начала слова), clj, cljs, edn, el, lisp; `%` — erl; `'` и `REM` — vb, vbs; `REM` и
  `::` в начале строки — bat, cmd; `"` — vim (в начале строки или после пробела, если до конца строки
  нет закрывающей кавычки; иначе строка), `#` vim9script; `--` — sql, lua, hs;
- блоки `--[[ ]]` Lua, `{- -}` Haskell, `<# #>` ps1, `#= =#` jl, `#| |#` Common Lisp, `#[ ]#` Nim,
  `<!-- -->` html, xml; блоки kt, scala, swift, rs, dart, hs, jl, fs, nim и lisp вкладываются;
- vue и svelte — однофайловый компонент: содержимое `<script>` и `<style>` разбирается по атрибуту `lang`
  (без него — JavaScript и CSS; `ts`, `tsx`, `jsx`, `scss`, `sass`, `less`, `stylus` и др.; неизвестный `lang`,
  например `coffee`, — без комментариев); в разметке вне них текст — данные (`//` в URL — не комментарий),
  `<!-- -->` — комментарий, код с `//` и `/* */` — выражения `{{…}}` Vue и `{…}` Svelte (у Svelte и в теге; `{/if}`,
  `{:else}` — не код);
- символьные литералы — данные: `?#` Ruby и Elixir, `$%` Erlang, `\;` Clojure, `?;` Emacs Lisp,
  `#\;` Common Lisp; Elixir `@doc`, `@moduledoc`, `@typedoc` со строкой — комментарий (документация);
- `/` в начале выражения (после `(`, `,`, `=`, `/`, `return`, `)` условия `if`, `while`, `for`, `with` и подобных; не
  после значения — `a / b` деление) — регулярное выражение в js, jsx, mjs, cjs, ts, tsx, mts, cts (`/\/\//`, `/[/]/g`
  — данные), незакрытое в строке кончается с ней; в groovy, gradle — slashy-строка (`/http://x/`), многострочная, с
  подстановками `${…}` (в них — код), начало выражения — как у лексера Groovy (после ключевого слова и любого знака,
  кроме значения: имени, числа, `this`, `null`, `true`, `false`, `)`, `]`, `}`, кавычки, `++`, `--`; перевод строки
  внутри `(` и `[` не начинает выражение), без закрытия до конца файла — деление; dollar-slashy `$/…/$` —
  многострочная; строка Groovy в кавычках с `\` в конце строки продолжается на следующей; в js, jsx, tsx `<` в начале
  выражения с именем тега — разметка JSX: текст между тегами — данные (`<p>see http://x.y</p>`), в теге `//` и `/* */` —
  комментарии, в `{…}` — код; тег, не закрытый до конца файла, — не тег;
- блочный скаляр YAML (`key: |`, `- >-`) под ключом скрипта — `run`, `script`, `before_script`, `after_script`,
  `install`, `before_install`, `after_success`, `after_failure`, `before_deploy`, `after_deploy`, `shell`, `command`,
  `commands`, `cmd`, `entrypoint`, `bash`, `pwsh`, `powershell` (и с пространством имён: `ansible.builtin.shell`),
  ключи `build.jobs` Read the Docs (`pre_build`, `post_build` и др.); у элемента `- |` — под ключом своего списка, у
  индикатора на строке после ключа — под этим ключом — разбирается как shell без общего отступа (тело heredoc —
  данные); вход `script` под `with:` шага с `uses: actions/github-script` (`uses` выше или ниже `with:`) — как
  JavaScript;
  под прочим ключом скаляр — данные: заголовок
  Markdown в `value: |` формы issue и в `description: |` OpenAPI — не комментарий;
- `package.json` и `composer.json` — код без комментариев.

Строковые литералы — данные, в том числе многострочные: шаблоны JS и raw-строки Go в обратных
кавычках, long string Lua, raw-строки Rust, C++, C#, F#, Swift (`#"…"#`) и Nim (`r"…"`), тройные
кавычки, многострочные строки Clojure и Lisp, Ruby, Perl, Julia, PowerShell; регулярки и литералы `%` Ruby
(`%w(…)`, `%r{…}`), операторы-кавычки Perl (`q{…}`, `qr{…}`, `s{…}{…}`), сигилы Elixir (`~r/…/`). Подстановки
`${…}` шаблонов JS и `#{…}` строк Ruby — код: комментарий в них виден. Файл с BOM UTF-16 или UTF-32 декодируется
по нему; строка текста, в которой git насчитал несколько строк (байт 0x0A внутри других знаков), отбирается, если
добавлена любая из них. Предел — 300 строк и 16 КиБ, при обрезке судье
сообщается об этом. Синтаксис известен для каждого расширения `CODE_EXTS` и имени `CODE_NAMES`.
Извлечение ограничено сроком `judge_stop.COMMENTS_BUDGET` (20 с); файлы, не разобранные в срок, судье
передаются списком без проверки, с предупреждением, и судятся по самоотчёту агента. Рубрика —
`rules/docs.md` и `rules/comments.md` с подставленными языками (`{DOC_LANG}`, `{COMMENT_LANG}`). Директивы
языка и инструментов (`//go:build`, `# type: ignore`, SPDX и т. п.) судья за комментарии не считает.

### Детектор зависимостей

Хук `PreToolUse` на `Bash` — детерминированный: без модели и без лимита отказов. Команда режется на
сегменты по `&&`, `||`, `;`, `|`, `&`, `(`, `)` и переводам строки вне кавычек: текст в кавычках, в том числе
многострочный и ANSI-C `$'…'`, — данные; `\` в конце строки продолжает сегмент; `#` в начале строки или после
пробела вне кавычек — комментарий до конца строки. Подстановка `$(…)`, `` `…` `` и `<(…)`, `>(…)` вне кавычек —
свой сегмент, а сегмент вокруг неё продолжается с заглушкой `$` на её месте. Сегмент разбирается на слова по
правилам shell: кавычки и `\` сняты. Перенаправления (`>log`, `2>&1`, `&>/dev/null`, `<file`, `> log`)
отбрасываются вместе с целью; оператор в кавычках (`">"`) — обычное слово. В начале сегмента отбрасываются
присваивания окружения (`A=1`, `PATH+=:/x`; в кавычках это имя команды, не присваивание), ключевые слова shell
(`if`, `then`, `do`, `!`, `{`, `coproc` и др.) и обёртки с их флагами: `sudo`, `doas`, `env` (строка `env -S` —
снова команда), `time`, `timeout` с длительностью, `nice`, `nohup`, `exec`, `command`, `builtin`, `xargs`,
`stdbuf`, `setsid`, `busybox`, `ionice`, `flock` с файлом; `su`, `runuser` и `flock` с `-c` — строка оболочки, как
`sh -c`: флаги `su` и `runuser` разбираются как getopt (`-c`, `--command`, `--session-command`, в том числе в склейке
`-lc '…'`), у `runuser -u пользователь [--] команда` команда — слова после флагов, без `-c` и `-u` слова за именем
пользователя — аргументы оболочки пользователя (`su app -- -c '…'` — это `sh -c '…'`), без них оболочка читает команды
из heredoc, here-string или конвейера (`echo 'npm i x' | su app`), `-s`/`--shell` задаёт программу вместо оболочки
(`su -s /usr/bin/npm app -- install x`); `watch` без `-x`/`--exec`
склеивает слова команды пробелом в строку `sh -c` (`watch -n 5 'npm i x'`), с `-x` — команда. Команда сравнивается по
имени файла без суффикса Windows и без учёта регистра:
`.venv/bin/pip`, `/usr/bin/npm`, `npm.cmd`, `NPM` — это `pip` и `npm`. Склейка коротких флагов (`-qr`) читается как
флаги, в том числе у `python`: `python -Im pip`, `python -Impip` — это `python -m pip`; буква флага со значением
забирает остаток склейки значением (`sudo -uroot npm install x` — `sudo -u root`). Слова команды разбираются в
пределах 4096 символов от её первого слова (`depcheck._WORDS_LIMIT`): длинные присваивания и обёртки перед ней
предел не съедают.

Вложенные команды проверяются тем же разбором, до 4 уровней: строка `sh -c '…'` (`sh`, `bash`, `zsh`,
`dash`, `ksh`, `fish`), аргументы `eval`, подстановки `$(…)` и `` `…` `` внутри двойных кавычек,
here-string оболочки без скрипта (`bash <<< '…'`), вывод `echo` и `printf` с аргументами-литералами в оболочку без
скрипта или `source` (`echo 'npm i x' | bash`, `bash <(echo …)`, `source <(…)`; маркер — у приёмника), удалённая
команда `ssh`, строка `trap`, команда `find -exec … ;`, `cmd /c`, `pwsh -Command`, `nix develop -c`, `nix shell -c`,
`nix-shell --run`, `mise exec --`, команда после `uv run`, `poetry run`, `pipenv run`, `conda run`, `pdm run`,
`rye run`, `hatch run` (и `hatch run окружение:команда`), `pixi run`, `python -m` (и `-m pip.__main__`),
`pipx runpip <окружение>` и программа пакета у `npm exec|x`, `pnpm dlx|exec`, `yarn dlx|exec`, `bun x`, `bundle
exec`. Тело heredoc (`<<EOF`, `<<'EOF'`, `<<-EOF`) до строки-терминатора — данные, но подстановки `$(…)` и
`` `…` `` в теле с терминатором без кавычек — команды (bash раскрывает их); `<<` внутри `${…}`, `$[…]` и
арифметики — не heredoc. У `sh`, `bash`, `zsh`, `dash`, `ksh`, `fish` без скрипта (или со скриптом `-`,
`/dev/stdin`) и без `-c` (или с `-s`) и у `ssh` без удалённой команды тело heredoc — команды; строка с самим `<<`
проверяется. Heredoc внутри `"$(…)"`, открытой до конца строки, — тело со следующей строки до терминатора, данные
(`git commit -m "$(cat <<'EOF'` … `EOF` `)"`), а у оболочки без скрипта (`x="$(bash <<EOF` … `EOF` `)"`) — команды;
строки после закрытия кавычки проверяются. Кавычки внутри `"$(…)"` вложены:
`gh pr create --body "$(printf "1) pip install x")"` — текст, не команда; heredoc в подстановке может
открываться и на следующей строке (`git commit -m "$(` ⏎ `cat <<'EOF'` … `EOF` ⏎ `)"`).

Отклоняется добавление названного пакета — в проект или глобально:

- JavaScript: `npm install|i|add` (и сокращения `install`), `pnpm add|install|i`, `yarn add`,
  `yarn global add`, `yarn workspace <имя> add`, `bun add|install|i`, `deno add|install`, и они же через
  `corepack <менеджер>`, `npx`/`bunx`/`pnpx <менеджер>` (`npx -y pnpm add x`), `npm exec|x`, `pnpm dlx|exec`,
  `yarn dlx|exec`, `bun x`;
- Python: `pip`/`pip3`/`pip3.11 install` (и с общими флагами pip перед подкомандой: `pip -q install`,
  `pip --proxy … install`), `python -m pip install` (`python3.12`, `pypy`, `py`), `uv add`,
  `uv pip install`, `uv tool install` (и пакеты `--with`), `pipx install`, `pipx inject`, `pipx runpip`,
  `pipenv install`, `poetry add`, `poetry self add`, `conda`/`mamba`/`micromamba install` и `create` с пакетами,
  `pdm add`, `rye add|install`,
  `pixi add`, `pixi global install`;
- другие языки: `go get`, `go install <пакет>@<версия>`, `cargo add`, `cargo install` (и с
  toolchain: `cargo +nightly install`), `gem install`, `bundle add`, `composer require`, его псевдоним
  `r` и сокращения от `req` (и `composer global require`), `dotnet add package`,
  `dotnet tool install`, `dart`/`flutter pub add` и `pub global activate`,
  `swift package add-dependency`, `mix archive.install`/`escript.install`, `cabal install`,

  `conan install --requires`, `R`/`Rscript -e 'install.packages(…)'` и подобные вызовы;
- системные: `apt`, `apt-get`, `aptitude install`, `brew install`, `dnf`, `yum`, `microdnf install`,

  `port install`, `snap install`, `flatpak install`, `nix-env -i`, `nix profile install`.

У менеджеров известны глобальные флаги перед подкомандой и флаги со значением (у uv — сверены с
`--help` uv 0.12). Не считаются
добавлением: установка по манифесту или lockfile без названного пакета (`npm ci`, `npm install`,
`pip install -r req.txt`, `vcpkg install`, `conan install .`), значения флагов (`--prefix`, `-C`,
`--omit` и подобные), локальные пути (`.`, `./x`, `/x`, `~`, `file:`, `name@file:…`; у pip — любое
слово со `/` без схемы), пакеты своего workspace (`workspace:`, `link:`, `portal:`, в том числе
`имя@workspace:*`; `pnpm add --workspace`), `--path` у `cargo add|install` и `bundle add`, пробный прогон
(`--dry-run` у pip и менеджеров `depcheck._DRY_RUN_MANAGERS`, у которых это пробный прогон или ошибка разбора;
yarn и прочие незнакомый флаг пропускают и ставят пакет — у них это установка; у npm — по разбору флагов npm: действует
последний из `--dry-run` и
`--no-dry-run`, значение `true`/`false` следом или после `=` — значение флага, так что `npm install --dry-run false x`
и `npm install --no-dry-run x` — установка; `true`/`false` за любым флагом без `=` перед подкомандой npm — значение
флага: `npm --dry-run false install x` — установка; у apt и apt-get — `-s`, `--simulate`, `--just-print`, `--dry-run`,
`--recon`, `--no-act` с булевым значением apt: `no`, `false`, `off`, `0` и подобные после `=`, в склейке (`-s0`) или
следующим словом, а также `--no-simulate` — установка; уровень `-q 2` у apt — значение флага, не подкоманда; у
aptitude — `-s` и те же длинные имена; у brew — `-n` и склейка с ним, `-vn`), архивы (`*.whl`,
`*.tar.gz`, `*.tgz`, `*.zip`, `*.gem`, `*.deb`, `*.rpm`, `*.nupkg` и др.), установка через pip только `pip`,
`setuptools` и `wheel` по имени из индекса (например, `pip install --upgrade pip`; `pip @ URL` — пакет), `conda
create` только с `python` и `pip`, разовый запуск без установки (`npx`, `bunx`, `uvx`,
`pipx run`, `go run`, `pnpm dlx`, `npm exec`; запуск менеджера ими — `npm exec pnpm add x` — проверяется), обновление,
поиск и удаление пакетов, текст после `#` в комментарии. URL
со схемой, кроме `file:`, — пакет; `-e git+https://…` у pip (и `--editable=…`, `-egit+…`) — тоже. Суффикс Windows
снимается в любом регистре (`NPM.CMD
install x` — это `npm install x`).

Отказ говорит агенту: новая зависимость — вопрос автору; назовите пакет, зачем он и что из
stdlib или установленного не закрывает; прочитайте `rules/dependencies.md`. Когда автор
согласился, агент повторяет команду с маркером `PLANKA_DEP_OK=1` прямо перед командой установки в её
сегменте (например, `cd app && PLANKA_DEP_OK=1 npm install left-pad`): это текстовый маркер внутри
команды, а не переменная окружения. Маркер засчитывается среди ведущих присваиваний сегмента, в том
числе после `sudo`, `env`, `if`, и покрывает строку `sh -c`/`eval` своего сегмента, но не подстановки
`$(…)` в нём; маркер в кавычках, в комментарии или в другом сегменте проверку не снимает. Команде установки, где
пакет или подкоманда под сомнением (см. «Известные ограничения»), отказ называет довод сомнения; если пакета она не
добавляет, агент повторяет её с тем же маркером. Отказы пишутся в журнал с `verdict: deny-dep`.

#### Манифесты

Пакет можно добавить и мимо команды установки: вписать в манифест и поставить по нему (`npm install`,
`uv sync`, `pip install -r`). Поэтому тот же хук `judge_tool.py` сравнивает имена зависимостей в
манифестах — без модели и без лимита отказов. Манифесты (`manifests.kind`):

- `package.json` — `dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`;
  псевдоним `npm:настоящее@версия` — настоящий пакет; `overrides`, `resolutions`, `pnpm.overrides` — только
  ключ, который ставит другой пакет (`npm:`) или источник не из реестра: версия лишь закрепляет пакет;
- `composer.json` — `require`, `require-dev`, кроме платформенных (`php`, `hhvm`, `ext-*`, `lib-*`,
  `composer`, `composer-plugin-api`, `composer-runtime-api`), и `repositories`, кроме `path`;
- `pyproject.toml` — `build-system.requires` (кроме стандартных бэкендов сборки `manifests._BUILD_BACKENDS`:
  setuptools, wheel, hatchling, flit-core, pdm-backend, poetry-core, uv-build, maturin, scikit-build-core,
  meson-python; прочее в `requires` проверяется), `project.dependencies` и `optional-dependencies`,
  `dependency-groups`, `tool.uv.dev-dependencies`, `tool.pdm.dev-dependencies`, `tool.poetry` —
  `dependencies`, `dev-dependencies` и группы (без `python`), `tool.hatch.envs.*` — `dependencies` и
  `extra-dependencies`; индексы uv, poetry, pdm; свои extras проекта (`app[cli]`) — не пакет;
- `requirements*.txt`, `requirements*.in` и `*.txt`, `*.in` в каталоге `requirements/` — строки
  требований; URL — имя из `#egg=` или из имени файла `.whl`, иначе не виден; индекс (`-i`, `--index-url`,
  `--extra-index-url`) и `-f`, `--find-links` по URL — источник; `-r`, `-c` и прочие опции — не пакеты;
- `Cargo.toml` — `dependencies`, `dev-dependencies`, `build-dependencies` (и в `target.*`),
  `workspace.dependencies`, `patch.*`, `replace`; `package = "…"` — настоящее имя крейта;
- `go.mod` — директивы `require` и модуль-замена из другого пути в `replace`; `Gemfile`, `gems.rb` — `gem '…'` с
  буквальным именем (операторы одной строки делит `;`) и `source "url"`, кроме RubyGems.

Пакет не из реестра по умолчанию — git, URL, другой реестр (`git:`, `github:`, `source:` и блоки `git`, `github`,
`source` в `Gemfile`, `git`, `registry` в `Cargo.toml`, `name @ url` PEP 508, спецификатор npm не из реестра) —
имя вида `имя @ источник`, источник для всех пакетов (индекс, репозиторий composer, `source` Gemfile) —
`index <url>`: смена источника у известного имени — новое имя, другой коммит, тег или ветка того же источника — нет;
источник архива по URL (`.whl`, `.zip`, `.tar.gz`, `.tgz` и т.п.) — каталог URL без имени файла и запроса: другая
версия файла в том же каталоге — не новое имя, другой хост или каталог — новое.

Местные зависимости — путь, `workspace:`, `file:`, `link:`, `{ path = … }`, `workspace = true`, источник
`[tool.uv.sources]` с `workspace` или `path` (в списке источников — если местный хоть один), `gem` с `path:`
или `:path =>`, `replace x => ./…` (`../`, `/`) в `go.mod` — не пакеты; имя пакета самого проекта (`name`
манифеста, `module` `go.mod`) — тоже не внешнее, если манифест есть в версии HEAD или ref до начала сессии или
он член workspace корня (`workspaces` корневого `package.json`, `[tool.uv.workspace]` корневого `pyproject.toml`):
имя свежего манифеста вне workspace пишет кто угодно. Имена PyPI сравниваются по PEP 503, Composer и crates.io — без
регистра (у crates `_` — как `-`), остальные — как записаны. Реестр вида (`manifests.registry`): `package.json` — npm,
`composer.json` — packagist, `pyproject.toml` и файлы требований — PyPI, `Cargo.toml` — crates.io, `go.mod` — go,
`Gemfile` — rubygems; «другой манифест проекта» ниже — манифест того же реестра, не обязательно того же вида.
Транзитивные не проверяются: строки `// indirect` в
`go.mod`. Файл требований с заголовком генератора (`autogenerated by`, `@generated by`) или аннотацией `# via`
(pip-compile, `uv pip compile`, `uv export`, `pdm export`) проверяется, как любой файл требований: такой заголовок
впишет и агент. Перегенерация с новым транзитивным пакетом — отказ или блок; обход — `PLANKA_DEP_OK=1` перед
командой.
Манифесты под служебными каталогами `snapshot.IGNORED_DIRS` и каталогами `fixtures`, `__fixtures__`,
`testdata`, `node_modules`, `site-packages`, `dist-packages`, `vendor`, `bower_components`
(`manifest_watch.FOREIGN_DIRS`, путь — от проекта, в git и вне его) не проверяются.

- Правка `Write`, `Edit`, `MultiEdit` манифеста: манифест — путь от корня проекта или путь с разрешёнными
  символическими ссылками (`deps.json` → `package.json`, каталог-ссылка `build` → `.`), тогда проверяется цель
  ссылки. Хук вычисляет текст после правки по входу инструмента и
  отклоняет её, если в нём есть имя, которого нет ни в тексте до правки, ни в версиях файла в репозитории
  (HEAD и источник незавершённых merge, pull, cherry-pick, rebase, revert — `manifest_watch._REPO_REFS` — и
  стороны конфликта в индексе `:1:`, `:2:`, `:3:` — `_INDEX_STAGES`, их пишет и конфликт `git stash pop|apply`,
  `git merge --squash`, `git cherry-pick -n`; одним `git cat-file --batch`), ни в других манифестах того же
  реестра в проекте и в его версии HEAD (манифест, убранный `git rm`), ни в `setup.py`, `setup.cfg`, `Pipfile`
  версии HEAD (только источник известных имён, и только закоммиченный: правку этих файлов хук не проверяет, поэтому
  их рабочее дерево имён не даёт; строковые литералы `install_requires`, `setup_requires`,
  `tests_require`, `extras_require` в `setup.py`, `[options]` и `[options.extras_require]` в `setup.cfg`,
  таблицы пакетов `Pipfile`), ни среди пакетов самого проекта: откат к закоммиченному проходит, конфликт
  незавершённой операции не даёт ложного отказа. Новый файл — все его имена. `Edit` и `MultiEdit` сопоставляют
  `old_string` с текстом, где CRLF приведены к LF, как Claude Code. Правку, которую инструмент сам
  отклонит (`old_string` не найден или неоднозначен), хук пропускает молча.
  Отказ говорит: после согласия автора добавьте пакет командой `Bash` с маркером `PLANKA_DEP_OK=1` —
  менеджером пакетов или правкой файла (`PLANKA_DEP_OK=1 python3 -c …`); правка файловым инструментом с
  новым именем отклоняется всегда. В журнал — `deny-dep` хука `manifest`. Манифест после правки не
  разобран, до правки не разобран и в репозитории его нет, больше 1 МиБ (`manifest_watch.MAX_MANIFEST_BYTES`),
  не обычный файл (FIFO не вешает хук), не прочитан или манифестов проекта больше `MAX_MANIFESTS` (не сравнён с другими
  манифестами) — пропуск с
  предупреждением и `skipped` в журнал.
- Команда `Bash`, которая не добавляет пакет: перед ней хук снимает имена всех манифестов проекта (в git —
  `git ls-files` отслеживаемых и неотслеживаемых, не исключённых git; вне git — обход без
  `FOREIGN_DIRS`) в `state/<session>.manifests.json`, после неё (`PostToolUse`, при неудаче —
  `PostToolUseFailure`) разбирает заново манифесты с другим размером, mtime или ctime и новые. Имя, которого нет
  в снимке (ни в одном манифесте того же реестра, ни среди пакетов самого проекта) и в версии HEAD, — блок
  `PostToolUse`: команда уже выполнена, а правка уже в файле, и хук не знает, чья она (команда могла
  вернуть работу автора). Работа автора узнаётся по ref, названному в команде git (`git stash pop|apply`,
  `git merge --squash`, `git checkout <ref> -- <пути>`, `git restore --source`, `git cherry-pick -n`;
  `manifest_watch.command_refs`): если коммит ref (у stash — коммит stash) старше начала сессии — первого
  вызова `judge_tool.py` на `PreToolUse` в ней, `state/<session>.start.json`, — имена из манифестов ref
  (у `stash -u` — и неотслеживаемых) не новые. Так же у `git apply <файл патча>` (операнд или `< файл`; относительный
  путь — от каталога команды): если файл не менялся с начала сессии (его ctime раньше начала; ctime ставит ядро при
  любой записи, `touch` назад его не ставит), слова изменённых строк манифестов в патче не новые. Причина велит не
  откатывать манифест вслепую, а спросить автора, откатывать только свою правку и повторять команду с маркером только по
  согласию; в журнал — `block-dep`. Манифест, не разобранный до или после команды, — предупреждение. Снимок не снят
  (манифестов больше `manifest_watch.MAX_MANIFESTS` = 1000, вне git файлов больше `MAX_WALK_FILES` = 20 000, срок, сбой
  каталога состояния; у команды с ref или патчем — имена не прочитаны за срок, манифестов в дереве ref больше
  `MAX_MANIFESTS` или git не прочитал дерево) — предупреждение раз на сессию и `skipped` в журнал на каждую команду,
  команда идёт без этой проверки. Команда, где `PLANKA_DEP_OK=1` стоит перед командой в её сегменте (ведущее
  присваивание, как у детектора зависимостей), не снимается и не сравнивается; в комментарии, аргументе и внутри `bash
  -c "…"` маркер не виден. Файл требований, который пишет генератор (`pip freeze > requirements.txt`, `uv export
  -o …`), проверяется по содержимому, как прочие манифесты: хук не знает, выполнился ли генератор и писал ли он
  последним (`echo x >> requirements.txt; false && pip freeze > requirements.txt`); новые имена — блок, обход —
  `PLANKA_DEP_OK=1 pip freeze > requirements.txt`.

### Запись в память

`planka/guard_memory.py` судит запись в постоянную память — память инструмента вне репозитория.
Каталог настроек — `CLAUDE_CONFIG_DIR`, без него `~/.claude`. Цель — файл, если путь файлового
инструмента (`~` раскрыта, относительный — от `cwd` входа хука) — это `CLAUDE.md` каталога настроек,
`*.md` под его `rules/`, файл под `projects/<проект>/memory/` или `projects/<проект>/agent-memory-local/`,
память субагентов — под `agent-memory/` каталога настроек (`memory: user`) или
`.claude/agent-memory-local/` проекта (`memory: local`; проект — `CLAUDE_PROJECT_DIR`, без неё `cwd`
входа), — или под `autoMemoryDirectory` (абсолютный путь). Память — ещё `CLAUDE.local.md` в каталоге проекта,
над ним и в его подкаталогах и файлы, которые импортом `@путь` подключают `CLAUDE.md` и `*.md` под `rules/`
каталога настроек и `CLAUDE.local.md` проекта и каталогов над ним — прямо или через импортированные, не дальше 4
переходов (`guard_memory.IMPORT_DEPTH`); путь импорта — от каталога файла с импортом или от `~/`, импорт в блоке
кода, коде в строке и HTML-комментарии не считается, файл больше 4 МиБ не разбирается, как у Claude Code. Такой
файл, если он файл рабочего дерева git проекта, не исключённый git, — файл репозитория, а не память; импорты
проектного `CLAUDE.md` памятью не считаются. Разбор импортов на вызов ограничен `guard_memory.MAX_IMPORT_FILES`
(200) файлами и `MAX_IMPORT_BYTES` (16 МиБ): остаток не разбирается, с предупреждением. В облачной сессии
(`CLAUDE_CODE_REMOTE_MEMORY_DIR`) те же `agent-memory/` и `projects/<проект>/memory/`,
`projects/<проект>/agent-memory-local/` судятся и под этим каталогом. Значение `autoMemoryDirectory`
берётся из всех источников сразу: `managed-settings.json` и `managed-settings.d/*.json`
(`/etc/claude-code`, на macOS `/Library/Application Support/ClaudeCode`), `.claude/settings.local.json` и
`.claude/settings.json` проекта, `settings.json` каталога настроек, и `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE`
(только абсолютный путь, `~` не раскрывается); Claude Code применяет одно по приоритету, хук судит запись
под любым — лишний вызов судьи дешевле пропуска. Под `autoMemoryDirectory` или cowork, который равен проекту
или содержит его, файл рабочего дерева git проекта, не исключённый git (`.gitignore`, `.git/info/exclude`,
`core.excludesFile`), — файл репозитория, а не память, и не судится (файл вложенного репозитория внутри
проекта — не файл рабочего дерева проекта, он память); под каталогом строго внутри проекта или вне его
судится всё. Значение, указывающее на сам проект, не отдаёт судье каждую запись в проекте. Память
субагента `memory: project` (`.claude/agent-memory/` проекта) — отслеживаемый файл репозитория, не
судится. Путь с нулевым байтом записью не считается. `..` в пути схлопывается до разрешения ссылок, как это
делает сам Claude Code перед хуком (`ссылка/..` — каталог, где лежит ссылка). На файловой системе без учёта
регистра пути сравниваются без учёта регистра. Пути сравниваются и как написаны, и с
разрешёнными символьными ссылками: если `CLAUDE.md`, `rules/`, `projects/<проект>` или `memory/` —
ссылки (dotfiles), судится и запись через ссылку, и запись прямо в её цель; ссылка вне каталога настроек,
ведущая внутрь этих мест, тоже судится. MCP-инструмент
`mcp__<сервер>__<инструмент>` — цель, если в имени инструмента есть слово действия записи (создать,
изменить, удалить, переименовать, перенести запись; список — `guard_memory.WRITE_VERBS`) и оно
относится к памяти: в имени сервера есть слово памяти (`guard_memory.MEMORY_WORDS`, например `memory`,
`remember`) — тогда любое такое слово в имени инструмента; иначе в имени
инструмента слово действия стоит перед словом памяти не дальше чем через одно слово
(`delete_all_memories`, `save_to_memory`) или сразу после него (`memory_add`); `remember`,
`memorize`, `memorise` — сами себе пара. Слова — по разделителям и границам camelCase, без учёта
регистра; аббревиатура и цифры — отдельные слова (`saveLTMemory`, `storeMemory2`). Целью не считаются
`mcp__redis_memorystore__set_key` (`memorystore` — не слово памяти) и
`mcp__x__memory_usage_set_alert` (действие относится к `usage`, а не к памяти).

Реплика автора — то, что написал человек: его запрос, сообщения, отправленные посреди хода, и ответ при отклонении
инструмента (они дописываются к реплике). Уведомления о фоновых задачах (`task-notification`), сообщения других агентов,
локальные команды вроде `/model` и служебные вставки Claude Code репликой автора не считаются и её не сбрасывают.

Судья видит прежние реплики автора (вместе — до 8000 символов), реплику автора текущего хода, ответы автора
на `AskUserQuestion` после неё, последнее сообщение агента перед репликой автора, последнее сообщение агента
перед записью, цель и текст записи (содержимое `Write`, новые строки `Edit`, `MultiEdit`, `NotebookEdit`,
аргументы MCP-инструмента JSON); каждое поле — не длиннее 8000 символов (поля автора —
`prompts.MAX_AUTHOR_FIELD`, остальные — `guard_memory.MAX_FIELD`). Запись проходит, если
автор явно согласился сохранить именно этот факт, записываемое с согласием совпадает и в записи нет
секретов. Отказ советует спросить автора «Сохранить в память: <факт>?».

### Повторная неудача команды

`planka/debug_watch.py` считает неудачи каждой команды `Bash` подряд в `state/<session>.debug.json`:
команда — её текст без краевых пробелов и с пробельными промежутками, схлопнутыми в один пробел;
неудача — событие `PostToolUseFailure` (прерывание пользователем не считается), успех той же команды
(`PostToolUse`) сбрасывает её счётчик, успех другой — нет. Каждый субагент (`agent_id` входа) и
основной агент считают отдельно: неудача одной команды у двух агентов — не «второй раз подряд». Код
выхода 1 (первая строка `error` —
`Exit code 1`) у команды, для которой он — ответ «не найдено», «ложно» или «различаются», — не
неудача и тоже сбрасывает счётчик: `grep`, `egrep`, `fgrep`, `zgrep`, `rg`, `test`, `[`, `[[`,
`diff`, `cmp`, `pgrep`, `pkill`, `pidof`, `which`, `type`, `command -v`/`-V`, `git grep`,
`git diff`/`diff-index`/`diff-files` с `--quiet`, `--exit-code` или `--no-index`,
`git merge-base --is-ancestor` и команда с отрицанием `!`. Команда берётся последняя в строке (после
`|`, `&&`, `||`, `;`, перевода строки; `&&` и `||` внутри `[[ … ]]` и строки тела heredoc командами не
считаются, `<<` внутри арифметики `$((…))` и `((…))` — сдвиг, а не heredoc), после присваиваний `VAR=…` и
обёрток `sudo`, `env`, `time`,
`nice`, `nohup`, `timeout`, `command`, `exec`, `builtin`; код 2 и выше у них — неудача. Команда
`echo`, `printf`, `true` или `:` без перенаправлений (`<`, `>` вне кавычек и экранирования: `echo "a > b"` —
не перенаправление)
после `&&` код не меняет — берётся команда перед
ней (`grep -q x f && echo found`); у присваивания `x=$(…)` — команда подстановки. На второй неудаче подряд
(`debug_watch.REPEAT_THRESHOLD`) хук добавляет агенту контекстом строку «Команда `…` упала второй
раз подряд — дальше, пожалуйста, по модулю <каталог rules плагина>/debugging.md.» и текст модуля
`debugging.md`, не чаще раза за реплику автора каждому агенту. Модель не вызывается, в журнал не пишется. Файл хранит
последние `debug_watch.MAX_COUNTS` (500) счётчиков команд и `MAX_SHOWN` (100) отметок показа: тронутая запись
становится свежей, самые давние вытесняются. Имя команды, обёртки и подкоманда git читаются по первым 4096 символам
команды.

### Судья, лимит и журнал

Судья — вложенный `claude -p` с `--setting-sources ""`, поэтому хуки плагинов в нём не
загружаются; вторая защита — `PLANKA_JUDGE=1`. Инструменты у судьи отключены (`--tools ""`): он
только читает промпт и отвечает JSON по схеме. Судья умирает вместе с хуком: `claude` запускает
процесс-сторож (`python3`), который раз в 0,5 с проверяет, жив ли хук, и при его смерти убивает всю
группу процессов судьи — `claude -p` и его потомков; ту же группу он убивает и после завершения `claude`: потомки
судьи хук не переживают. Хук, убитый по таймауту или прерыванием, не
оставляет работающий `claude -p`. Промпт и аргументы уходят судье в UTF-8
при любой локали; корень проекта, транскрипт, файл плана и цель записи в память по путям с кириллицей
находятся и в локали без UTF-8. Модель судьи — настройка `judge_model`; при `session` — модель сессии из событий
`SessionStart` (поле `model`) и `PostModelSwitch` (поле `to_model`), которые записывает `planka/model_watch.py`; без
неё — модель последнего ответа основной ветки транскрипта (`transcript_path`); не нашлась — судья запускается без
`--model`, на модели `claude` по умолчанию, с предупреждением один раз за сессию. `SessionStart` без `model` (после
`/clear`, при восстановлении сессии) известную модель не стирает; `PostModelSwitch` без годного `to_model` —
предупреждение, модель не меняется.

Отказ приходит агенту как ошибка инструмента или как причина продолжить работу; причина
начинается с `planka: Мой дорогой друг, `. Причину судья пишет агенту на «вы», без обращения: его добавляет хук.
Причина блока `Stop` заканчивается просьбой не пересказывать ответ, уже показанный автору, — написать только, что
исправлено или подтверждено, и коротко повторить вопрос, если он был (`judge_stop.RETELL_NOTE`).
Не больше двух отказов на одну реплику автора для одного хука (вопрос, план, запись в память, `Stop`) — в лимит
входят отказы судьи и детерминированный отказ плана по владению файлами; после двух отказов следующая проверка
пропускается без вызова судьи с предупреждением `planka: лимит отказов, пропущено без проверки`. На отказы детектора
зависимостей и проверки манифестов лимит не распространяется.

Журнал вердиктов: `judge.log` в `$CLAUDE_PLUGIN_DATA`, по строке JSON на решение хука: вердикт
судьи (`ok`, `deny`), его пропуск (`skipped`) и лимит (`budget`), а также решения без вызова судьи —
`deny-dep` (отказ команде установки, хук `bash`, и правке манифеста, хук `manifest`), `block-dep` (блок
после команды, добавившей зависимость в манифест, хук `manifest`), `deny-files` отказа плана по файлам и
`skipped`, когда нет плана или рубрики или манифест не проверен. Вызов хука без проверки (команда Bash
без добавления пакета и без новых имён в манифестах, сообщение без совпавшего фильтра, запись не в
память) в журнал не пишется. Строка хранит только метаданные: хук (`question`, `plan`, `bash`,
`manifest`, `memory`, `stop`), вердикт, причину, нарушенные пункты, сработавшие фильтры, длительность,
`content_len` и `content_sha256` проверенного содержимого, `files` (изменённые файлы хука `Stop`,
не больше `MAX_LISTED`; у `block-dep` — в поле `manifests` число манифестов с новыми именами), `added` (число новых имён
у `deny-dep` и `block-dep` хука `manifest`) и `tool` (инструмент записи в память или правки манифеста);
само содержимое не пишется. Отказ и блок по зависимости пишутся без причины: она цитирует команду или имена
пакетов; пропуск хука `manifest` — с описанием `error`, в нём путь манифеста. При размере от `LOG_MAX_BYTES`
(1 МиБ) файл переименовывается в `judge.log.1`; ротация и запись идут под блокировкой `judge.log.lock`. Ошибка
судьи пишется в журнал описанием без текста ответа модели; фрагмент ответа (до 200 символов) виден только в
предупреждении пользователю. Ответ хука выдаётся и при сбое записи журнала, вместе с предупреждением
«внутренняя ошибка». Сбой записи счётчика отказов — пропуск проверки с тем же предупреждением: без счётчика
нечем остановить цикл отказов.

Состояние — `state/` в `$CLAUDE_PLUGIN_DATA`: счётчики отказов, однократные предупреждения, снимок дерева и его неудачи
по корням, счётчики неудач команд, модель сессии, начало сессии и снимки имён манифестов перед командами `Bash`
(снимок, к которому не пришёл `PostToolUse`, — команду отклонили — удаляется следующим снимком через час); их запись и
чтение, кроме чтения модели и начала сессии (файл заменяется целиком), — под блокировкой `state/.lock`; битый файл или
JSON не того типа считается пустым. Файл сессии и брошенный временный файл `.tmp-*`, не менявшиеся 7 дней, удаляются; у
начала сессии каждый вызов `judge_tool.py` на `PreToolUse` обновляет время изменения. Вход и ответ хука — UTF-8
независимо от локали.

## Известные ограничения

- Фильтр «готово» — словесная эвристика и даёт ложные срабатывания: «прошёл», «зелёный», `done`
  или `complete` в обычной прозе. Цена ложного срабатывания — лишний вызов судьи; судья такое
  сообщение пропускает, если оно не заявляет о выполненной работе. Прочие глаголы прошедшего времени
  («обновил», «удалил», «переписал», английские `implemented`, `added`) фильтр не ловит; ложно срабатывает на
  «не исправил», «добавил бы».
- Фильтры «варианты» и «готово» смотрят только последнее сообщение агента: варианты или заявка
  «готово» в более раннем сообщении реплики фильтр не запускают, хотя судья, вызванный другим
  фильтром, их видит. Фильтр «варианты» — текстовая эвристика (два пункта списка и слово вроде
  «вариант», «рекомендую», «option»); сообщение с вариантами в прозе он пропустит.
- Детектор зависимостей знает только перечисленные менеджеры (нет, например, `pkg`, `pkg_add`,
  `emerge`, `guix`, `xbps-install`, `nimble`, `cargo binstall`, `Pkg.add` Julia) и только перечисленные обёртки,
  запускатели и оболочки: не разбираются `pnpm dlx -c '…'`, `npm exec -c '…'`, `direnv exec`, `devbox run`,
  `parallel`, `chrt`, `taskset`, `pwsh -EncodedCommand`, `sudo -s` со строкой, сокращения длинных флагов обёрток,
  которые принимает getopt_long (`su --comm '…'`, `runuser --us app -- …`, `watch --int 5 '…'`, `timeout --sig KILL 5
  …`), `su -s "$VAR" app` с командами из stdin; больше 16 обёрток подряд (`sudo`, `env`, `nice`, `su`, `runuser` и
  др.) разбор не снимает — сомнение; вход оболочки не из `echo`/`printf`
  (`curl … | bash`) и команда, чьё имя — подстановка или переменная без глагола установки следом (`$PY -m pip
  install x`), не проверяются (пропуск). Поимённый перечень форм — долг,
  `context/deferred/depcheck-enumerated-forms.md`.
  Имя пакета в
  переменной (`npm install $PKG`) отклоняется, хотя пакет неизвестен. Флаг со значением вне известных наборов
  после подкоманды: его значение считается пакетом (ложный отказ); форма `--flag=value` разбирается всегда. Строка,
  которую собирает подстановка (`bash -c "$(…)"`, `eval "$(…)"`), не вычисляется: проверяются только команды самой
  подстановки. Пробный прогон из окружения или конфига (`npm_config_dry_run=true`, `apt-get -o APT::Get::Simulate=true`)
  не виден (ложный отказ). `--dry-run=false` и `--no-dry-run` у менеджеров, где флаг без значения (pip, cargo, uv,
  poetry, composer, pnpm), не разбираются: менеджер падает с ошибкой разбора, а детектор такую команду отклоняет.
- Отказ с сомнением: менеджер и команда установки распознаны, а пакет или подкоманда под сомнением, или команда стоит
  за 16 обёртками подряд (любая; маркер — в начале сегмента, до обёрток). Причина отказа
  называет довод; команду, которая пакета не добавляет, агент повторяет с `PLANKA_DEP_OK=1`. Формы: флаг вне
  известных наборов со словом следом перед подкомандой (`npm --weird val i x`; проверяются первые 4 такие пары,
  дальше — пропуск; флаг без значения перед иной подкомандой, за которой слово установки и имя, `npm -g help
  install x`, — ложный отказ); `--dry-run` сразу за флагом со значением этого менеджера (`pip install --target
  --dry-run x`; у cargo, uv, composer такая команда и так падает с ошибкой разбора); команда установки без пакета
  под `xargs` (`echo x | xargs npm install`; локальный путь из stdin — ложный отказ); вложенность глубже 4 уровней
  — текст глубже разбирается по словам без кавычек, текст в кавычках там похож на команду (`… -m 'a; npm install
  x'` — ложный отказ); команда установки без пакета в первых 4096 символах от имени команды и слово-не-флаг дальше
  (слово не пакет — ложный отказ); `eval` или оболочка, чья строка `-c` или скрипт стоят за этим пределом; имя
  команды — подстановка или переменная, за ним глагол установки и слово-не-флаг (`$M install x`, `$(which npm) i
  x`; не менеджер — ложный отказ).
- Проверка манифестов знает только манифесты из «Манифестов» (нет, например, `setup.py`, `setup.cfg`,
  `Pipfile` — имена их версии HEAD только известные: перенос закоммиченного файла в `pyproject.toml` не новое имя, —
  `environment.yml`,
  `pom.xml`, `build.gradle`, `*.csproj`, `pubspec.yaml`, `mix.exs`, `deno.json`); в `Gemfile` — только `gem` с
  буквальным именем; конец блока `path … do` ищется по `do`, ключевым словам блока и `end` в начале строки:
  иная запись (`x = if …`, два блока в одной строке, блок в одну строку `source "url" do; gem "a"; end`) сдвигает его —
  гемы за блоком не видны или местный гем
  внутри считается внешним (`source "url"` без блока — новый источник на любой глубине и в любом операторе строки
  через `;`, гем с `git:`, `github:`,
  `source:` внутри `path … do` — с источником); URL в требованиях без `#egg=` и не `.whl` не виден; архив по URL с
  версией в каталоге,
  а не в имени файла (`…/releases/download/v1.0/x.whl`, `files.pythonhosted.org/packages/…/<хеш>/x.whl`), или без
  расширения архива (`codeload.github.com/…/tar.gz/v1`): смена версии — новое имя с источником, ложный отказ, обход —
  маркер до правки. Пропускаются: новая прямая
  зависимость `go.mod`, помеченная `// indirect`; источник пакетов вне манифеста (`.npmrc`, `pip.conf`,
  `.cargo/config.toml`, `go.work`, `GOPROXY`, `UV_INDEX_URL`); команда, которая сама же коммитит манифест
  (`… && git commit -am x`): имя уже в HEAD; манифест вне корня проекта (`cd /tmp/x && …`), в подмодуле, во
  вложенном репозитории, исключённый git или под `FOREIGN_DIRS`; имя, уже объявленное в другом манифесте того
  же реестра в проекте (в том числе другого вида: `requirements.txt` и `pyproject.toml`), и имя пакета самого
  проекта — манифеста версии HEAD, ref до начала сессии или члена workspace корня (`workspaces` `package.json`,
  `[tool.uv.workspace]` `pyproject.toml`); имя из `setup.py`, `setup.cfg`, `Pipfile` версии HEAD и ref команды до начала
  сессии — их правка не
  проверяется, коммит такой правки (`git commit` агента) делает имя известным; стандартный бэкенд
  сборки в `build-system.requires` (`manifests._BUILD_BACKENDS`); правка файловым инструментом при числе
  манифестов проекта больше `MAX_MANIFESTS` (1000); команда, чьи имена ref не прочитаны за срок снимка или чьё
  дерево ref держит больше `MAX_MANIFESTS` манифестов (снимок не снят, предупреждение); имя со стороны
  конфликта в индексе (`:1:`, `:2:`, `:3:`), в том числе из stash, созданного в сессии (`git stash pop` с
  конфликтом); все гемы в блоке `path … do … end` и `gem` с `path:`;
  источник `[tool.uv.sources]` со списком, где местный хоть один; пакеты в `vendor`, `build`, `dist`,
  `target`; `Edit`, чей `old_string` отличается от файла кавычками; правка манифеста после ответа
  `PostToolUse` (фоновая команда `run_in_background`); `Edit`, чей `old_string` в файле дословно не найден, —
  хук считает, что инструмент его отклонит. Стадии индекса агент может записать сам
  (`git update-index --index-info`), как и `MERGE_HEAD` (`.git/MERGE_HEAD` файлом): обход в два шага —
  записать сторону конфликта с новым именем, затем правка манифеста с этим именем проходит. Маркер
  `PLANKA_DEP_OK=1` в сегменте команды ведущим присваиванием снимает сравнение манифестов со всей команды.
  Ложный отказ: `setup.py`, где требования собирает код (чтение файла, цикл, функция), — их имена не видны,
  перенос в `pyproject.toml` отклоняется; перенос из незакоммиченного `setup.py`, `setup.cfg`, `Pipfile` (новый
  или изменённый после коммита) и из любого такого файла в проекте вне git — их рабочее дерево имён не даёт:
  закоммить файл до переноса; член npm workspace, ссылающийся на соседа, которого ещё нет
  (`"@acme/ui": "*"` до создания `packages/ui/package.json`), — имя внешнее, пока сосед не создан: создай
  соседа первым или укажи `workspace:*`; имя пакета свежего манифеста вне workspace корня — внешнее: член
  `pnpm-workspace.yaml` (файл не читается), член Cargo workspace без `path`, модуль `go.work`, сосед в проекте
  вне git: зависимость на такого соседа отклоняется, пока его манифест не закоммичен (вне git — всегда). Файл требований
  с заголовком
  генератора или `# via` проверяется по содержимому, как и файл, куда пишет генератор: перегенерация (`pip freeze >
  requirements.txt`, `pip-compile`, `uv export -o requirements.txt`), добавившая транзитивный пакет, блокируется
  после команды — с согласия автора агент запускает генератор с `PLANKA_DEP_OK=1`, а правку такого файла файловым
  инструментом делает командой с маркером. Ложный блок: имя, пришедшее не из версий `_REPO_REFS`, не из сторон
  конфликта, не из другого манифеста того же реестра и не из ref до начала сессии, — `git apply` патча из stdin,
  heredoc или конвейера, из файла, изменённого в сессии, больше 1 МиБ или по относительному пути от другого каталога
  (`cd` в команде, `git -C`), перенос
  командой `Bash` из незакоммиченного `setup.py`, `setup.cfg`, `Pipfile`,
  `npm create` с новыми пакетами, `git stash pop` и `git checkout <ref> -- <манифест>` из ref моложе начала
  сессии (в том числе созданного автором в другом терминале за время сессии), ref команды
  `git -C <другой репозиторий>` (ищется в репозитории проекта) или неразобранной формы, — и правка манифеста
  другим процессом между снимком и сравнением засчитываются команде. Пропуск: имя из ref с датой коммиттера
  раньше начала сессии — поддельной (`GIT_COMMITTER_DATE`) или ref, созданного агентом в прошлой сессии, — и из файла
  патча, записанного агентом в прошлой сессии, проходит как работа автора: git не хранит, кто создал ref; дата
  коммиттера и запись reflog берут одну `GIT_COMMITTER_DATE`; ctime объекта не подделать, но у коммита, полученного
  `git fetch` в сессии, он тоже в сессии. Слово из изменённых строк манифеста в старом патче проходит, даже если
  команда вписала его иначе. Начало сессии, где `judge_tool` не вызывался дольше 7 дней (`STATE_TTL`), пишется
  заново: ref и патчи до этого перерыва проходят как старые; маркер внутри
  `bash -c "…"` не виден, и такая команда блокируется. Отклонённую правку после согласия автора агент
  делает командой с маркером. Цена — каждая команда `Bash`: `git rev-parse` и `git ls-files` с разбором всех
  манифестов проекта перед ней и `git ls-files` со `stat` после, до 5 с на каждую сторону
  (`manifest_watch.SNAPSHOT_BUDGET`, `CHECK_BUDGET`), у команды с ref — ещё `git cat-file --batch` коммитов ref
  и на каждое дерево ref до начала сессии `git ls-tree -r` и `git cat-file --batch` манифестов, в том же сроке
  снимка; у `git apply` — чтение файлов патчей до 1 МиБ в том же сроке; после команды, если новые имена остались, — `git
  ls-tree -r` и `git cat-file --batch` версии HEAD; у правки манифеста — один `git cat-file --batch` на версии
  `_REPO_REFS` и стороны конфликта (`HEAD_TIMEOUT`), а если новые имена остались, — обход манифестов проекта и чтение
  версии HEAD (`SNAPSHOT_BUDGET`).
- `judge.log` содержимого не хранит, но поле `reason` — текст судьи и может цитировать проверенное
  содержимое (строки комментариев, фрагменты плана, записи в память). Секрет в командной строке,
  закомментированный ключ в `toml`/`yaml`/`ini` или секрет в записи в память уходит к судье в промпте.
- Модель сессии (`judge_model` = `session`) берётся из событий `SessionStart` и `PostModelSwitch` (Claude Code
  v2.1.251+), а без них — из транскрипта; пропущенный `PostModelSwitch` (версия Claude Code до 2.1.251, хук не уложился
  в срок) оставляет судье прежнюю модель до следующего события. Сообщения агента за реплику (судья `Stop`) и реплика
  автора (судья записи в память) берутся из транскрипта (`transcript_path`), а формат транскрипта не документирован.
  Человек отличается от служебных записей полем `origin` (Claude Code 2.1.293); в транскрипте без него репликой автора
  считается любая запись пользователя с текстом, в том числе локальная команда; в транскрипте, начатом версией без
  `origin` и продолженном версией с ним, прежние реплики старой части судьям не видны. Модель не нашлась — судья на
  модели `claude` по умолчанию с предупреждением; сообщения реплики не нашлись — судья видит только последнее сообщение,
  с предупреждением один раз за сессию. Список `options` в настройке требует Claude Code v2.1.271+; полный id модели
  вместо алиаса не выбрать.
- Показ `systemMessage` для событий `UserPromptSubmit`, `PreToolUse` и `Stop` взят из общего раздела
  документации по хукам и вживую не проверен.
- Хуки записи в память (`guard_memory.py`), повторной неудачи команды (`debug_watch.py`) и модели сессии
  (`model_watch.py`) вживую не проверены: только тестами с подменой `claude`.
- Сторож судьи проверен только на Linux; на macOS и других платформах не запускался.
- Судья записи в память видит только файловые инструменты и MCP-инструменты со словом памяти в имени:
  запись в память командой `Bash` (`echo … >> ~/.claude/CLAUDE.md`) не проверяется; слитное имя вроде
  `mcp__openmemory__add` словом памяти не считается; глагол перед словом памяти, которое определяет
  другое существительное (`mcp__x__set_memory_limit`, `clear_memory_cache`), судится как запись в
  память, как и слово памяти в значении ресурса (`update_memory_request`, `set_memory`) — дешевле
  лишний вызов судьи, чем запись в память без согласия; действие, которого нет в
  `guard_memory.WRITE_VERBS`, и действие через два слова после слова памяти (`memory_bank_update`) не
  судятся. Символьная ссылка на файл внутри `rules/` или `memory/` каталога настроек судится только
  при записи через неё: запись прямо в её цель вне каталога настроек не проверяется (ссылка на каталог
  `rules/`, `memory/` или `projects/<проект>` — проверяется и так).
  `autoMemoryDirectory` из `--settings`, серверных managed-настроек и профиля MDM на macOS хуку
  не виден; относительное значение `autoMemoryDirectory` и `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE` не
  учитывается. Если `autoMemoryDirectory` равен проекту или содержит его, запись
  в файл проекта, который git не исключает, не судится: хук считает его файлом репозитория; память в
  таком каталоге судится, только если файл исключён git или лежит во вложенном репозитории. Без `git`,
  вне репозитория или при ошибке git такой файл судится как память. Импорты `CLAUDE.local.md` подкаталогов проекта
  не разбираются (Claude Code читает такой файл по требованию, хук не обходит проект на каждый вызов); сверх
  `MAX_IMPORT_FILES` или `MAX_IMPORT_BYTES` запись в остальные импортированные файлы не судится. Соседняя запись с
  тем же именем в другом регистре, ведущая в тот же файл (ссылка `Notes` → `notes`), принимается за файловую систему
  без учёта регистра: сравнение без учёта регистра даёт лишний вызов судьи. Глагол через два слова перед словом
  памяти (`addToAIMemory`: `add`, `to`, `ai`, `memory`) не судится.
- Повторная неудача — неудача той же команды, текст в текст с точностью до пробелов: та же проверка с
  другим флагом — другая команда. Счётчик не сбрасывается между репликами, только успехом команды.
- Код 1 команды-ответа из списка выше не считается неудачей и тогда, когда это проверка, которую
  агент ждёт зелёной (`grep -q ok out.log`, `test -f build/app`, `diff expected actual`): её повтор
  модуль не подмешивает. Код 1 цепочки `a && grep …`, где с кодом 1 упала `a`, тоже принимается за ответ
  `grep`, а код 1 самой `echo` или `printf` в `grep … && echo …` (ошибка вывода, неверный формат) — за
  ответ `grep`. Команда-ответ вне списка (`sort -c`, `git show-ref --verify`, `systemctl is-active`), под
  `xargs`, `bash -c`, в скобках или после одиночного `&` — неудача, как любая другая: скобка, открытая перед именем
  команды (`(grep x f)`, `{ grep x f; }`), делает команду неудачей; у подоболочки с цепочкой
  учитывается последняя команда (`(cd d && grep x f)`, `(make; grep x f)` — ответ `grep`). `#` начинает
  комментарий в начале слова, в том числе сразу после `;`, `|`, `&` и скобки (`grep x f;#c`).
  Арифметика `$((` или `((`, не закрытая до конца команды, делает сдвигом и каждый `<<` после неё: тело
  heredoc в такой команде читается командами. Флаг, делающий git-команду ответом (`--quiet`, `--exit-code`),
  дальше 4096 символов от начала команды не виден — код 1 такой команды считается неудачей. Счётчик команды,
  вытесненной из последних 500, начинается заново.
- Расширение кода вне `CODE_EXTS` и имя вне `CODE_NAMES` считаются «прочее» и проверку документации
  не запускают.
- Любая ошибка судьи (нет сети, таймаут, неразбираемый ответ, ответ не по схеме: `ok` не булево, `reason` не
  строка, `violated` не список строк) или самого хука — пропуск со
  предупреждением `planka: ...` в `systemMessage`, не блокировка. Сбой части «документация» хука
  `Stop` выключает только этот фильтр: «варианты» и «готово» проверяются.
- Детерминированная проверка файлов в плане разбирает такие формы (канонический формат назван в `rules/planning.md`):
  волна — заголовок `#… Волна N`/`Wave N`, строка `**Волна N**` или setext над `===`/`---`; задача — заголовок, жирная
  строка или setext `Задача N`/`Task N` с номером `N` или `N.M`, необязательной пометкой `(…)` и разделителем `:` `.`
  `—` `–` `-` или концом строки; строка файлов — `Файлы:`/`Файл:`/`Files:`/`File:` (с жирным до двоеточия) отдельной
  строкой или пунктом списка; пункты — маркеры `-` `*` `+`, `1.`, `1)`, префиксы Create/Modify/Test/Delete/ Update/Edit,
  Создать/Изменить/Тест/Удалить/Обновить, в том числе с пометкой в скобках перед двоеточием
  (`Create (temp only, not committed):`); пути — в обратных кавычках через пробелы, запятые, пометки `(…)` и связки `и`,
  `and`, `или`, `or`, `+`, `&` перед следующим путём в кавычках (`` `a.py` и `b.py` `` — два файла) или токены через
  запятую (точка или `;` в конце строки, в том числе после пометки `(…)`, отбрасываются); `./a.py` и `a.py` — один файл;
  задача, повторённая с тем же номером, — одна задача. Любой заголовок закрывает задачу; заголовок не волны и не задачи
  уровнем не глубже волны закрывает волну. Жирная волна (`**Волна N**`) получает уровень первого заголовка своей задачи:
  её закрывает заголовок не волны и не задачи уровнем не глубже этого (`#### Шаги` под `### Задача 1` волну не
  закрывает, `### Итог` закрывает), а до первой задачи — любой такой заголовок; при задачах жирной строкой любой
  заголовок закрывает и волну. Задача без строки файлов, задача вне волны и задача с `Файлы: нет` в проверке владения не
  участвуют; без задач с файлами план целиком проверяет модель. После пустой строки список файлов продолжают только
  пункты, которые целиком путь, или пункты с префиксом. Пункт списка файлов, который не путь и не префикс владения
  (`- **Не трогать:**`, `- Read-only:`), пропускается вместе с пунктами, вложенными под него глубже; пункты,
  вложенные под саму строку `Файлы:`, — владение. Путь без префикса с пометкой чтения — в скобках сразу за путём
  или после тире в конце серии путей — не владение: две задачи волны, читающие один файл, не конфликтуют. Пометка —
  текст (`planparse._READ_NOTE`), который начинается с «только чтение», «только для чтения», «только читать», «чтение»,
  «читать», «не трогать», «не менять», «не изменять», «не править», «без изменений», «не изменяется», «только импорт»,
  «для справки», «только для справки», «справочно», «справка», «контекст», «read-only», «readonly», «read only», «read»,
  «reading», «read access», «no changes», «without changes», «unchanged», «reference», «reference only», «context»,
  «context only», «import», «imports only», «do not»/«don't» + «modify»/«edit»/«touch»/«change», и дальше кончается или
  идёт `,` `;` `:` `.` или тире через пробел; «чтение конфига», «read-write», «reference implementation», «без изменений
  в API» пометкой не считаются. Пометка вне списка («новый», «добавить X») оставляет путь владением: две задачи,
  правящие один файл, остаются конфликтом. Пометка относится к одному пути перед ней; путь с префиксом владения остаётся
  владением и с пометкой; пункт без префикса с двумя пометками в скобках подряд путём не считается и пропускается.
  Повторная строка файлов в задаче, за путями в обратных кавычках которой идёт законченное предложение — текст,
  кончающийся на `.`, `!` или `?` («Файл: `cfg.yaml` читается при старте.»), — описание, не владение; первая строка
  файлов задачи, повторная с одними путями, с путями без кавычек, с пояснением после тире или с незаконченным хвостом
  (`` Файлы: `b.py` for tests ``) — владение. Пропуск дешевле ложного отказа: задача, которая пометила файл чтением, но
  правит его, конфликт по нему не даст — его увидит только судья. Не разбираются fenced-блоки и `<!-- -->`; незакрытый
  `<!--` прячет остаток плана. Путь с пробелом не читается; строка над `===` всегда считается заголовком; строка,
  начинающаяся с одного–шести `#`, вне fenced-блока — заголовок, в том числе без пробела после `#` (`###Задача 1`); семь
  и больше `#` — не заголовок. BOM в начале плана снимается.
- Вне git снимок — обход всего дерева со `stat` каждого файла; он ограничен только сроком 7 с
  (`remind.SNAPSHOT_BUDGET`), числа файлов предел не задаёт. Очень большое дерево (порядка 3 млн файлов на тёплом кэше
  ФС) в срок не укладывается: снимок не делается, фильтр «документация» не запускается, предупреждение одно; неудача
  запоминается для корня, и снимок этого корня до конца сессии не повторяется — таймаут даже на холодном кэше ФС
  выключает фильтр «документация» для корня на всю сессию. В git предел `snapshot.MAX_FILES` (50 000) ограничивает
  только число изменённых и неотслеживаемых путей: их больше — так же без снимка.
- Строки комментариев извлекаются по синтаксисам из `comments.py` — свой у каждого расширения кода, но разбор упрощён.
  Регулярное выражение JS и slashy-строка Groovy отличаются от деления по предыдущему токену; разметка JSX — только в
  js, jsx, tsx. В Ruby `/` и `%` после слова через пробел и вплотную к следующему знаку — литерал-аргумент
  (`puts /#/`), если слово не локальная переменная — имя, которому раньше в файле присвоено значение или которое
  названо параметром метода в скобках или блока (`a = 4` и `a /b` — деление); локальной считается и переменная
  другого метода, а регулярка-аргумент кончается со строкой. В Perl `/` после слова, которое не встроенная функция,
  так же — регулярка-аргумент: деление на свою константу (`PI /2`) прячет остаток строки; так же `<<` после своей
  функции — heredoc только с идентификатором с `-`, `~`, в кавычках или с заглавной буквы. В многострочной регулярке
  (`qr{…}`, `%r{…}`, `~r(…)`, `/…/` в начале выражения) `#` после пробела — комментарий, только если за закрытием
  литерала стоит флаг `x`. Вторая часть `s{…}{…}` — и на следующих строках, за пробелами и комментариями; код замены
  только с флагом `e`, разбирается до четырёх вложенных `s{…}{…}e`. Блочный скаляр YAML со скриптом под ключом не из
  списка (`args:` Kubernetes, свой ключ) — данные, его комментарии судье не уходят; вход `script:` actions/github-script
  читается как JavaScript при `uses:` шага выше или ниже `with:`, входы-скрипты прочих действий — по правилам shell. Во
  vue и svelte код в атрибутах-директивах Vue (`@click="a() // c"`) и в атрибутах Svelte в кавычках — данные, его
  комментарии судье не уходят; `<template lang="pug">` разбирается как HTML; `<script>` и `<style>` с неизвестным
  `lang` — без комментариев. В Perl `}` анонимного хеша или функции принимается за конец оператора: `=слово` в первой
  колонке следующей строки читается POD.
  Строка, которая начинается с тройных кавычек, считается docstring Python, даже если это продолжение выражения.
  Однострочные строки в sh, yaml, sql, php, R, erl, vb, ex — только в пределах строки. Многострочная строка или литерал
  без закрытия до конца файла читается однострочным. После `__END__` и `__DATA__` в Ruby и Perl — данные (POD в них —
  документация). UTF-16 и UTF-32 узнаются только по BOM. В Vim `"` после пробела — комментарий, только если до конца
  строки нет второй `"`: комментарий с кавычкой внутри (`let x = 1 " say "hi"`) читается строкой. Docstring Clojure и
  Emacs Lisp — строка, а форма под `#_` Clojure — код: судье они не уходят. Clean-фильтр git, меняющий число строк,
  сбивает отбор добавленных строк. Переименованный файл целиком, а не против старого пути, — если он перенесён `mv` без
  `git add`, изменён больше, чем git считает переименованием (по умолчанию сходство меньше 50 %). Файл кода читается
  целиком, без предела размера.
- Корень проекта под репозиторием выше отделяется от него только по `CLAUDE_PROJECT_DIR`, только если вершина —
  домашний каталог или его предок и репозиторий под каталогом запуска не отслеживает ни одного файла. Сессия,
  запущенная в самом домашнем каталоге-репозитории dotfiles, снимает весь `~` (`git status --untracked-files=all`):
  снимок упирается в предел или срок и для этого корня больше не повторяется. Проект без своего git под
  репозиторием в другом месте (не дом и не его предок) считается частью этого репозитория. Если за сессию в
  отделённом корне появится отслеживаемый файл репозитория дома, корень сменится на вершину, и сверка документации
  этой реплики пропустится (снимок другого корня). Если домашний каталог — сама вершина рабочего репозитория
  (контейнер с `HOME=/app` при репозитории `/app`), новый неотслеживаемый подкаталог становится корнем: соседи
  workspace не видны проверке манифестов, `CLAUDE.md` вершины не находится.
- Вне git `.gitignore` читается упрощённо: учитываются имена без подстановочных знаков и записи
  вида `*.ext`; `/name` и `name/` трактуются как имя на любой глубине поддерева; отрицания `!имя`
  пропускаются, и возвращённый ими файл в снимок не попадает.
- Ядро делится на части по строкам, начинающимся с `## `: такая строка внутри блока кода в `philosophy.md` стала
  бы границей части (блоков кода в ядре сейчас нет). Предупреждение о нечитаемом `philosophy.md` приходит от каждой
  части.
- Правка только документации фильтр «документация» не запускает. Без `prompt_id` во входе хука
  снимок, лимит отказов и показ модуля `debugging.md` привязаны к пустому id: фильтр сравнивает дерево
  со снимком последней реплики, лимит отказов общий на всю сессию, модуль показывается каждому агенту
  раз за сессию.
- Субагенты не получают напоминания: у них нет реплик автора. Философия при проблеме едет
  внутри текста задачи в плане — судья плана проверяет, что она там есть.

## Проверка

```bash
make test           # unittest, claude подменяется tests/stub/claude
make test-hostile   # тот же прогон в локали C, вывод latin-1, хуки в ascii; заодно — изоляция тестов
make validate       # claude plugin validate . и plugin: маркетплейс и плагин
make check          # test, test-hostile и validate
```

Устойчивость к чужому git-конфигу пользователя проверяет `tests/test_hostile_git.py`, в обеих целях тестов:
снимок, сверка изменений, извлечение комментариев, список манифестов и их версии в HEAD и хуки `remind`/`Stop`
под конфигом с `color.ui=always`, `diff.noprefix`, `diff.external`, `status.showUntrackedFiles=no`,
`core.attributesFile` с `-diff` и textconv-драйвером и подобными дают тот же результат, что без него, в том
числе под `diff.interHunkContext` и `diff.renames=false` и с `.gitattributes` проекта, где файлы кода —
`binary`; `core.excludesFile` пользователя уважается. Изоляцию тестов `make test-hostile` проверяет чужими
`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT`/`KEY`/`VALUE`, `GIT_CONFIG_PARAMETERS` и `XDG_CONFIG_HOME/git`,
`CLAUDE_PROJECT_DIR` и `CLAUDE_CONFIG_DIR` (`context/testing.md`).
