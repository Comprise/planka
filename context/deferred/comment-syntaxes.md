# Разбор комментариев: свои слова Perl, области видимости Ruby, вложенность s{…}{…}e, входы-скрипты действий

**Что не так.** `comments._comments` разбирает файл без полного разбора языка (`context/architecture.md`,
«Комментарии изменённых файлов»); остаются:

- Perl: `/` и `<<` после голого слова, которого нет в `comments._PERL_TERM` и `comments._PERL_VALUE` (своя функция,
  константа, импорт), решает правило «аргумент вызова»: `/` вплотную к следующему знаку — регулярка
  (`comments._literal_opens`), `<<` — heredoc, если идентификатор с `-`, `~`, в кавычках или с заглавной буквы
  (`comments._heredoc_ok`); вплотную `foo<<EOS` — сдвиг. say, fc, evalbytes — так же (функции только с feature);
- Ruby: `names` (`comments._ruby_locals`) — все имена файла, которым присвоено значение, без областей видимости
  (`def`, `class`, `module`): имя, введённое в другом методе, считается локальным — `/` и `<<` за ним деление и
  сдвиг, хотя это вызов метода; по той же причине регулярка-аргумент (`puts /a`) кончается со строкой, а у Ruby
  многострочна;
- вторые части `s{…}{…}e` глубже `comments._MAX_CODE_DEPTH` (4) не разбираются как код;
- вход `with:` действия, кроме actions/github-script, разбирается как shell.

Следствие — лишняя строка «комментария» у судьи документации или пропущенный комментарий.

**Чем доказано.** Вызовом `comments._comments`: `"x = PI /2 # c\n"` (`pl`) → `[]` (perl: `'PI' / 2`, `# c` —
комментарий); `"def f\n  a = 1\nend\ndef g\n  a /b # c\nend\n"` (`rb`) → `[(5, "# c")]` (Prism: `a` в `g` — метод,
`/b # c` — регулярка); пять и шесть вложенных `s{a}{` с `f() # d` внутри и `}e` (`pl`) → `[]`, четыре — комментарий
найден.

**Верное решение и цена.**

- Perl: точного статического решения нет. Регулярка или деление, heredoc или сдвиг за словом зависят от того,
  объявлена ли к этому месту функция и с каким прототипом; функции ставит `use Module` — `import` исполняется при
  компиляции и может завести имя, вычисленное во время работы (`*{"main::$name"} = sub () {…}`). Разобрать без
  исполнения кода нельзя (доказательство Кеглера «Perl cannot be parsed»). Точная часть уже сделана — встроенные
  слова (`_PERL_TERM`, `_PERL_VALUE`, сверены с `perl -MO=Deparse`). Из точных мер осталась бы одна: имена,
  объявленные в том же файле (`sub NAME`, `use constant NAME`), с учётом `package`; не сделана — среди 2309 файлов
  Perl машины формы `слово /x` со своей функцией не нашлось.
- Ruby: точное решение — таблица локальных переменных по областям видимости, а её даёт только парсер. Лексер Ruby
  сам спрашивает парсер (`lvar_defined` в parse.y, так же Prism); `end` метода находится, только если отличать
  модификатор `if`/`while` от оператора, а это решает состояние лексера, то есть те же `/` и `<<`. Цена — свой парсер
  Ruby. Ошибка сейчас дешёвая: лишнее имя в `names` делает `/` делением, а регулярку-аргумент однострочной.
- `s{…}{…}e`: точное линейное решение есть — один проход со стеком кадров. Кадр второй части разбирает её как код
  сразу, а не после закрытия, и считает свои скобки (правило Perl: скобки без учёта смысла); вложенные части считают
  только свои знаки, а закрытие обрезает разбор кадра. Цена — переписать `_parse` и помощники под границу строки;
  повторный разбор текста части держит предел линейности. Наибольшая глубина среди Perl машины — 3
  (Encode/MIME/Header.pm).
- Входы-скрипты прочих действий: язык входа задаёт реализация действия (`action.yml` и код в его репозитории нужной
  версии), не файл workflow; без загрузки действия не решить. Shell верен для большинства: `#` — комментарий и в
  bash, Python, Ruby, PowerShell.

**Почему отложено.** Ошибка здесь дешёвая: лишняя строка у судьи или пропуск комментария, судья документации всё
равно видит список изменённых файлов и сообщения агента. Вес низкий.
